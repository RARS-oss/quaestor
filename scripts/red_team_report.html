quaestor · red-team audit

Adversarial verification

Everyone fixes tasks. We closed the harness.

Four ways to fake an autonomous trading record — forge a number, drop a losing cycle, run with the network open, fake a risk proof — each run here for real against a signed quaestor receipt, and each one caught by the same offline binaries a judge can run.

4 / 4 fraud vectors caught
real binaries · real receipt · attacks on /tmp copies

The 2026 agent-benchmark trust crisis was never about whether an agent could do the task — it was that nobody could tell a real result from a doctored one. A logged number can be edited, a bad run can be deleted, a "sealed" score can be produced with the network wide open, and a risk claim can be asserted without proof. quaestor makes every one of those a detectable forgery. Below, each attack is executed and then caught.

VECTOR 04

Fake a risk proof

CAUGHT

The attackClaim every order's worst-case loss is under the hard cap without actually being under it — forge the risk attestation.

cap: 2^16 = $65,536 worst-case max loss

PROVED$ zkrisk prove 12000 16 > /tmp/rt/proof.jsonexit 0
(RiskProof JSON written)
VERIFIES$ /home/daniil/.cache/hack-target/release/examples/zkrisk verify /tmp/rt/proof.jsonexit 0
{"ok":true}
TAMPER$ python3 -c 'flip one nibble of proof hex'
proof[0]: e -> 1
REJECTED$ /home/daniil/.cache/hack-target/release/examples/zkrisk verify /tmp/rt/proof_bad.jsonexit 1
{"ok":false}
CANNOT PROVE$ /home/daniil/.cache/hack-target/release/examples/zkrisk prove 70000 16exit 1

Caught — Each order carries a Bulletproofs range proof that max loss < 2^16 USD. Tamper the proof and it fails to verify; feed an over-cap value and zkrisk prove refuses to emit a passing proof at all.
